# ADR-0010 — P-256 rather than X25519

**Status:** Accepted
**Date:** 2026-08-20

## Context

The link needs ECDH to establish a shared secret at pairing. The default modern
choice is X25519: smaller code, simpler constant-time implementation, no
invalid-curve pitfalls, no patent history, and a cleaner API.

The earlier plan in this project specified X25519 for exactly those reasons.

What changed the answer is the **device** silicon. Sensor nodes are STM32WL55,
which has a **PKA** hardware accelerator. The PKA accelerates NIST prime curves.
It does not help with Curve25519.

The hub is STM32H755, which has **no PKA at all** — verified against the HAL
driver set, which has `cryp`, `hash` and `rng` and no `pka`. On the hub, either
curve is software.

## Decision

**NIST P-256 (secp256r1)** for ECDH.

This follows the project's standing preference: *where the silicon accelerates one
option, prefer that option.*

## Consequences

- Devices do point multiplication in **hardware**. On a battery node doing this at
  pairing and at re-keying, that is a direct saving in both time and energy —
  and the device is the constrained end.
- The hub does P-256 in software via mbedTLS, whose implementation is constant-time
  and widely reviewed. The hub is mains-powered and the operation is rare, so the
  cost is irrelevant there.
- P-256 is universally supported, including by TLS — the same curve serves
  [the planned Ethernet TLS](../network/tls.md), so one curve covers both links.
- **P-256 is less forgiving to implement.** Point validation is mandatory: every
  received public key must be checked to be on the curve and not the point at
  infinity, or an invalid-curve attack recovers the private key. X25519 does not
  have this failure mode. The requirement is written into
  [security/wire-crypto.md](../security/wire-crypto.md) rather than left to memory.
- Larger wire format: 33-byte compressed points against X25519's 32 bytes, once
  [ADR-0018](0018-compressed-points-on-the-wire.md) settled the encoding. The
  original 65-byte uncompressed form did not fit the RFM69's 66-byte FIFO.

## Alternatives rejected

**X25519.** Better in every respect except the one that decides it — the
constrained end of the link has hardware for the other curve and none for this one.

**Ed25519 / ECDSA for signing as well.** Not yet needed; authentication currently
rests on an out-of-band key fingerprint. Revisit if devices ever need to
authenticate to something other than their own hub.
